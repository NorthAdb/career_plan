# 项目构思：两个简历项目怎么选、怎么做（2026-10-06）

## 0. 先给结论

| | 项目 A（纯 Agent） | 项目 B（Java 后端 × Agent） |
|---|---|---|
| **推荐方向** | **A1：tiny-agent —— 上下文工程优先的编码 Agent 引擎** | **B1：智识 —— 企业知识库智能问答平台（Java 原生 RAG + Agent）** |
| 一句话卖点 | 不是"调 API 的玩具"，而是把 pi / Claude Code 的核心机制复刻一遍并给出对比与评测数据 | 一套完整的 Java 工程底座 + 生产级 RAG/Agent，带评测数字，通吃 Java 岗与复合岗 |
| 语言 | TypeScript（延续你读过的 pi 栈；如果目标公司偏 Python 可用 Python 重写 loop，机制不变） | Java 21 + Spring Boot 3 + LangChain4j / Spring AI + PostgreSQL(pgvector) |
| 面试命中率 | Agent 岗的"上下文工程/复杂工具调用/评测"条款 | Java 岗全部八股载体 + Agent 岗 RAG 条款 + 复合岗 |
| 工期（每周 ~20h） | 6-8 周到可讲故事 | 8-10 周到可讲故事 |
| 风险 | 同类"mini claude-code"多，必须靠**机制深度 + 对比表 + 评测数字**区分 | 必须避免"套壳 CRUD"观感，靠**混合检索 + 评测量化 + 自研内核**区分 |

**联动卖点（眼前一亮的关键）**：B 的 Agent 层提供"双内核"——默认 LangChain4j 内核，可切换为你自研的 tiny-agent 内核（通过 A2A/MCP 或 HTTP 适配），README 里给出两内核在相同评测集上的表现对比。这样两个项目不是孤立的两行简历，而是一个故事："我自研了引擎，并验证了它在真实业务里与工业框架的差距/优势"。面试官极少见到这种写法。

## 1. 项目 A 候选方向（纯 Agent，选一个做深）

### A1（主推）tiny-agent：上下文工程优先的编码 Agent 引擎

**定位**：一个 ~3000-5000 行的 TS 库 + CLI，实现编码 agent 的全部核心机制，每个机制都有"为什么这么设计"的一页说明 + 与 pi / openai-agents / claude-code 的对比。

**机制清单（每条都是面试弹药）**：
1. **Agent loop**：LLM ↔ tool-call 循环；工具串行/并行执行策略；流式输出；循环上限与 abort 传播。
2. **Context 管理（核心差异化）**：
   - system prompt 组装顺序与缓存命中（prompt prefix 稳定性）
   - 工具结果截断策略（大文件读入 → 按行窗口 + 省略标记）
   - **auto-compact**：token 阈值触发的历史压缩（保留最近 N 轮 + 摘要注入），对比"不管理/截断/压缩"三种策略的评测数据
   - system-reminder 注入（把 todo 状态、环境变化以受控方式注入上下文）
3. **记忆**：AGENTS.md 式持久记忆（每次会话结束由 LLM 决定写入什么）+ 会话恢复（resume）。
4. **Subagent**：Task 工具派生隔离上下文的子 agent（fan-out 并行 + 结果回收），解释"为什么子 agent 能省主上下文 token"。
5. **工具层**：read/write/edit/bash/grep + todo + **MCP client**（接一个真实 MCP server，如 filesystem）。
6. **权限模式 + hooks**：只读/确认/全自动三档，工具调用前置检查。
7. **评测 harness（点睛之笔）**：自建 30-50 个小任务（文件整理、bug 修复、多步重构），跑 pass@1，输出不同 context 策略、不同模型下的对比表 → 你就有了"我做过 agent 评测"的实证，正中智谱/腾讯 JD 条款。

**简历 bullet 示意**：
> 自研 TypeScript 编码 Agent 引擎（~4k 行）：实现 tool-use loop、上下文自动压缩（阈值触发摘要 + 工具结果截断）、subagent 上下文隔离、MCP 接入与权限模型；自建 40 任务评测集，对比 3 种上下文管理策略，压缩策略使任务通过率从 X% 提升至 Y%、平均 token 消耗降低 Z%；README 提供与 pi / openai-agents 的机制对比表。

**为什么不是别的**：
- A2 Deep Research 多 agent（planner→并行 searcher→synthesizer）：演示效果好，但市面上太多，机制上不如 A1 贴你已有的源码积累。
- A3 记忆系统专项（对标 mem0/letta 做可插拔 memory 库 + benchmark）：学术味浓、适合读研/算法叙事；工程岗展示面窄。可以作为 A1 的一个模块长出来，不必单开。

### A1 的三周里程碑

- W1：loop + 工具层 + trace 日志（demo 已有雏形，见 `E:\zcode_test\demo-mini-agent`）
- W2：context 管理三件套（截断 / compact / reminder）+ 会话持久化
- W3：subagent + MCP client + 权限；之后用 2 周做评测集和对比实验

## 2. 项目 B 候选方向（Java 后端 × Agent，选一个做深）

### B1（主推）"智识"：企业知识库智能问答平台

**业务故事**（面试要能一句话讲清给谁用、解决什么）：
> 面向 50-500 人团队的私有知识库问答：员工用自然语言问"报销流程/历史故障方案/合同要点"，系统给**带引用溯源**的答案；管理员上传文档自动入库；所有数据不出内网（可切换本地模型）。

**架构分层（每一层都对应 Java 面试考点）**：
1. **接入层**：REST + SSE 流式问答；JWT 登录；多租户隔离（知识库属于部门）。
2. **Agent/编排层**：LangChain4j（或 Spring AI）ChatClient + 工具：
   - `kb.search`（混合检索）`sql.readonly`（Text2SQL 数据问答，B2 并入这里做杀手工具）`doc.fetch`（取原文段落做引用）
   - 多轮会话记忆（conversation memory 落库）；失败重试与工具超时控制
   - 可选内核：切换自研 tiny-agent（联动卖点）
3. **RAG 管道（核心）**：
   - 摄取（异步，走 MQ）：Tika/PDFBox 解析 → 分块（固定 512 + 重叠，再对比语义分块）→ embedding → PostgreSQL **pgvector**（HNSW）
   - 检索：**pgvector 向量 + PostgreSQL 全文检索(tsvector/BM25) 混合召回 → RRF 融合 → rerank** → top-k 带原文偏移，前端高亮引用
   - 这条链的每个环节都做成开关，跑评测出对比表
4. **存储层**：PostgreSQL（业务表 + pgvector + tsvector 一个库搞定，正中你"接 PostgreSQL"的想法）；Redis（会话缓存、热点答案缓存、分布式锁防重复摄取）；一条 MQ（文档摄取削峰）。
5. **平台层（区分度）**：Micrometer + Grafana 可观测（问答延迟、token 成本分用户统计）；Docker Compose 一键起；**评测 harness**：自建 100+ 问答对评测集，指标 = 答案准确率（LLM 当裁判）/ 引用命中率 / P95 延迟 / 每问成本，输出"分块策略 × 混合检索 × rerank"的消融对比表。

**简历 bullet 示意**：
> 基于 Spring Boot 3 + LangChain4j + PostgreSQL(pgvector) 的企业知识库问答平台：实现文档摄取流水线（MQ 异步 + 分块 + 向量化）、混合检索（向量 + BM25 + RRF 融合 + 重排）与引用溯源；Agent 层支持 6 个工具的多轮调用与只读 Text2SQL；自建 100 条评测集做消融实验，混合检索 + rerank 使答案准确率从 X% 提升至 Y%，P95 延迟 Z ms；支持多租户权限与 token 成本统计。

**避坑**：不要 clone ruoyi-ai 改皮——把它当业务壳参考（数据模型、后台管理），RAG 管道、Agent 层、评测全部自研；README 写清"自研 vs 借鉴"边界。

### B2 Text2SQL（并入 B1 的工具，不单开）
只读数据库账号 + JSqlParser 做 AST 白名单校验（禁 DDL/DML、强制 LIMIT）+ 执行超时 + 行数上限；用 Spider 中文子集或自建 schema 问答题跑准确率。面试讲到"如何安全地让 agent 碰生产数据库"，这是极好的深挖素材。

### B3 AI Code Review 机器人（备选）
GitHub/GitLab webhook → 拉 diff → agent 审查 → 行内评论。实用、演示好，但 Java 分布式深度展示弱，且 CR 类开源工具已多（CodeRabbit 等），区分度一般。

### B4 DeepWiki Java 版 / 代码库 Wiki 生成器（备选，炫技型）
对标 deepwiki-open（18k star）与 llmwiki（Karpathy 概念）：agent 克隆仓库 → 构建"文件树 + 关键模块"地图 → 逐层生成结构化 wiki 存 PostgreSQL → 增量更新。亮点：天然用你的 tiny-agent 当引擎，且正好呼应 llmwiki。风险：仓库解析与增量更新工程量大，5 个月内做完有压力。**折中方案**：把它做成 B1 的一个摄取源（"代码仓库也是一种知识库文档"），而不是独立项目。

## 3. 开源参与策略（配合两个项目，不单开战线）

1. **第 1 个 PR（11 月，练手）**：`a2aproject/a2a-java`（504 star、4 个 good-first-issue、官方背书）——先跑通它的 examples，挑一个协议测试或文档类 GFI。
2. **第 2 个 PR（12-1 月，与 B 同构）**：`langchain4j` 的 GFI（给某模型/向量库写 adapter）——你在 B 里本来就要写 pgvector/pgxxx 集成，一份努力两份产出。
3. **backup**：`agents-flex`（中文、响应快）。
4. 心态设定：PR 被合是意外之喜，**不被合的 PR 也能写进简历**（"向 langchain4j 提交 XXX 修复，参与了 code review 讨论"），何况你已经精读过 pi——把精读笔记整理成 issue/讨论/博客发出去，同样是社区存在感。

## 4. 通吃两类 JD 的叙事结构（面试 3 分钟版）

1. "我读透了两个一线 agent 的源码（pi 112k star / claude-code），发现它们真正的功夫在上下文工程，于是自研了一个引擎来验证这些设计" ——（项目 A）
2. "然后把引擎放到真实业务里检验：用 Java 做了一个企业知识库平台，双内核可切换，和 LangChain4j 在同一评测集上对比" ——（项目 B）
3. "我关心的不是能不能跑，而是跑得好不好：两个项目各有一张消融评测表" ——（量化数字）

这套叙事同时回答了 Java 岗的"项目深度"、Agent 岗的"机制理解"、复合岗的"业务落地"。
