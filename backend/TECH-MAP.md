## 先理清最容易混的四个词

很多人把"微服务、分布式、集群、K8s"混成一团。它们不是同一层的概念：

- **单体（Monolith）**：所有业务代码打成一个程序部署。`mall` 就是单体（虽然拆了 `mall-admin`、`mall-portal` 几个模块，但每个都是完整的 Spring Boot 应用，共用一个数据库）。
- **集群（Cluster）**：同一个程序部署多份，前面用 Nginx 做负载均衡。目的是扛流量、一台挂了还有别的。单体也可以做集群。
- **分布式（Distributed）**：系统跨多台机器协作，就会遇到单机没有的问题：多台机器怎么加锁（分布式锁）、怎么保证一致（分布式事务）、怎么生成不重复的 ID（分布式 ID）。**只要做了集群，就已经是分布式问题了**。
- **微服务（Microservice）**：把单体按业务拆成多个独立部署的小服务（订单服务、商品服务、用户服务），每个服务有自己的数据库，服务之间通过 RPC/HTTP 调用。它是"分布式"的一种组织方式，需要配套的注册中心、网关、配置中心等。
- **K8s（Kubernetes）**：管理成百上千个容器的平台，负责调度、扩缩容、故障重启。它是"怎么运行程序"的问题，和"怎么写程序"无关。

一句话串起来：**单体做集群就进入了分布式；业务大了把单体拆成微服务；服务多了用 K8s 管容器。** 实习生的项目做到"单体 + 集群 + 中间件"就够了，微服务和 K8s 要能讲清是什么、为什么需要。

## 掌握程度分三档

- **A 必会**：项目里真的用、面试必深挖。要能写代码、讲原理、讲踩坑。
- **B 会用**：能用起来，能讲核心原理。
- **C 知道**：能说清是什么、解决什么问题、和替代方案的区别。不需要动手。

## 二、数据存储

你的两个项目用"双库"：**MySQL 管交易，PostgreSQL 管 AI**。项目 A 里 mall 原有的业务表留在 MySQL；新增的向量知识库、会话记忆、工具审计、语义缓存、评测结果放 PostgreSQL。项目 B 从零写，直接全部用 PostgreSQL。

| 名词 | 解决什么问题 | 在电商里用在哪 | 你的项目里 | 档 | 面试常问 |
|---|---|---|---|---|---|
| **MySQL** | 持久化存储，事务保证数据正确 | 订单、商品、用户、退货申请 | 项目 A 业务库（mall 原有，不动） | A | B+ 树索引、最左前缀、事务隔离级别、MVCC、行锁/间隙锁、redo/undo/binlog、explain 看慢查询 |
| **PostgreSQL** | 功能更全的关系库：丰富的索引类型和扩展生态，向量、全文、JSON 都能在一个库里做 | AI 数据层 | 项目 A 的 AI 库；项目 B 的全部存储 | A | 和 MySQL 的区别、MVCC 实现差异与 VACUUM、GIN/GiST 索引、JSONB |
| **pgvector** | PostgreSQL 的向量扩展：存 embedding、按相似度检索 | 售后政策检索、商品语义搜索、历史故障案例检索 | 两个项目都用 | A | HNSW 和 IVFFlat 的区别、距离度量（余弦/内积/L2）、召回率和速度怎么权衡、为什么不用独立向量库 |
| **中文全文检索（zhparser / pg_trgm）** | 关键词精确匹配，弥补向量检索对专有名词、编号不敏感的短板 | 订单号、商品型号、政策条款号 | 和 pgvector 组成混合检索 | B | 中文为什么要分词、倒排索引、混合检索怎么融合排序（RRF） |
| **Redis** | 内存数据库：缓存热点、计数、加锁 | 商品详情缓存、登录态、库存预扣、分布式锁、限流 | 两个项目都用 | A | 五种数据结构及底层、持久化 RDB/AOF、缓存穿透/击穿/雪崩、缓存和数据库一致性、Redisson 锁原理 |
| **Elasticsearch** | 全文搜索、复杂筛选 | 商品搜索 | mall 的 `mall-search` 模块，保留不动 | B | 倒排索引、和 MySQL `LIKE` 比的优势、和 pgvector 混合检索怎么选 |
| **MongoDB** | 文档型数据库，结构灵活、写入快 | 浏览记录、收藏 | mall 的会员浏览记录 | C | 什么数据适合放 Mongo |
| **MinIO / OSS** | 对象存储，存图片和文件 | 商品图片、政策 PDF 原件 | mall 原有 | C | 为什么文件不存数据库 |

### MySQL 和 PostgreSQL 怎么选

| | MySQL | PostgreSQL |
|---|---|---|
| 国内使用 | 互联网公司主流，**八股必考** | 越来越多，AI 应用场景尤其多 |
| 强项 | 简单、读多写少的高并发、生态成熟 | 扩展生态（pgvector、全文、地理信息）、复杂查询、JSONB、数据类型丰富 |
| 向量检索 | 新版本开始支持，生态弱 | pgvector 是事实标准 |
| 你的用法 | 项目 A 交易数据 | 两个项目的 AI 数据 |

面试被问"为什么用两个库"时这样答：交易库要稳，AI 负载（批量写 embedding、向量检索）不应该和下单抢资源；AI 数据需要向量和全文检索，PostgreSQL 一个库就能搞定，不用再引入独立的向量数据库；代价是要处理跨库同步（商品数据从 MySQL 同步到 PostgreSQL），你用 MQ 事件加每日对账解决。

### Elasticsearch 和 pgvector 怎么选

| | Elasticsearch | PostgreSQL + pgvector |
|---|---|---|
| 擅长 | 海量文本全文检索、聚合分析 | 中小规模的向量 + 全文 + 结构化过滤，和业务数据在一起 |
| 运维 | 独立集群，吃内存 | 就是一个数据库 |
| 你的用法 | mall 原有商品搜索，保留 | 新增的语义检索 |

## 四、分布式问题（只要做集群就会碰到）

| 名词 | 解决什么问题 | 典型场景 | 档 | 面试常问 |
|---|---|---|---|---|
| **分布式锁** | 多台机器同时改同一份数据时互斥 | 防超卖、防重复下单 | A | `SETNX` + 过期时间的坑、Redisson 看门狗、锁误删 |
| **幂等** | 同一个请求执行多次，结果和执行一次一样 | 支付回调重复、MQ 重复消费、**LLM 重试工具调用** | A | 唯一索引、token 机制、状态机、去重表 |
| **分布式 ID** | 多台机器生成不重复且有序的 ID | 订单号 | B | 雪花算法、时钟回拨 |
| **跨库数据同步 / 本地消息表（Outbox）** | 一份数据要同时写进两个存储时，怎么保证不丢、不乱 | **项目 A：商品数据从 MySQL 同步到 PostgreSQL** | A | 先写库再发消息会丢什么、本地消息表怎么做、CDC（Canal / Debezium）是什么、为什么还要定时对账 |
| **限流 / 熔断 / 降级** | 流量过大或下游故障时保护系统 | 秒杀限流、下游超时熔断 | B | 令牌桶 vs 漏桶 vs 滑动窗口、熔断三种状态 |
| **分布式事务** | 跨多个数据库/服务的操作要么都成功要么都失败 | 下单扣库存 + 创建订单跨服务 | C | 2PC、TCC、本地消息表、最终一致性；Seata 是什么 |
| **CAP / BASE** | 分布式系统的理论取舍 | 选注册中心、选存储 | C | CAP 三选二的真实含义 |
| **分库分表（ShardingSphere）** | 单表数据太大时拆分 | 订单表上亿行 | C | 分片键怎么选、跨分片查询怎么办 |

## 五、微服务全家桶（C 档：知道是什么）

以 Spring Cloud Alibaba 为例，每个组件解决微服务拆分后冒出来的一个问题：

| 组件 | 解决的问题 |
|---|---|
| **Nacos** | 注册中心（服务 A 怎么找到服务 B 的地址）+ 配置中心（改配置不用重启） |
| **Spring Cloud Gateway** | 统一入口：鉴权、路由、限流（类似 Nginx 但在 Java 体系内，懂业务） |
| **OpenFeign / Dubbo** | 服务之间像调本地方法一样调远程接口 |
| **Sentinel** | 限流、熔断、降级 |
| **Seata** | 分布式事务 |
| **SkyWalking** | 链路追踪：一个请求经过了哪些服务、慢在哪 |

想看真实的微服务长什么样，对照 [mall-swarm](https://github.com/macrozheng/mall-swarm)（mall 的微服务版）浏览一下目录结构即可，**不要拿它做项目**：时间不够，而且微服务的复杂度在单人项目里讲不出价值。
