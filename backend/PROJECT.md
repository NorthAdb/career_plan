# 项目 A：电商智能售后 Agent（基于 mall 二次开发）

配图：[电商后端 + 售后 Agent](../diagrams/backend-stack/backend-stack.html)

![电商后端 + 售后 Agent](../diagrams/backend-stack/preview.png)

## 一句话

在开源电商系统 mall 上新增"智能售后"能力：买家用自然语言查订单、问政策、发起退货、找商品；客服看到 Agent 的预审建议后一键处理。**重点不是"接了个大模型"，而是让一个会出错、会重试、很贵的 LLM 安全、可控、低成本地操作有事务、有权限的业务数据。**

## 仓库与协议

mall 使用 Apache-2.0 协议。Fork 后保留原 LICENSE，README 开头写明"基于 [macrozheng/mall](https://github.com/macrozheng/mall) 二次开发"，并用一张表列出你新增和修改的模块，让面试官一眼分清哪些是你写的。你的代码集中在新模块 `mall-ai` 里，对原有模块的改动（例如商品修改时写 Outbox）尽量少，并在 README 里逐条列出。

## 数据层：双库

| 库 | 存什么 | 为什么 |
|---|---|---|
| **MySQL（mall 原有）** | 订单、商品、会员、退货申请等全部业务表 | 交易数据不动，避免花 1–2 周做和 AI 无关的迁移 |
| **PostgreSQL + pgvector（新增）** | 政策知识库、商品语义索引、会话记忆、工具审计、语义缓存、评测结果 | 向量 + 全文 + 结构化过滤一个库搞定；AI 负载不压交易库 |

PostgreSQL 主要表（W10 设计文档里细化）：

| 表 | 关键字段 | 用途 |
|---|---|---|
| `kb_chunk` | 文档 ID、条款编号、正文、`embedding vector`、`tsv tsvector` | 售后政策混合检索 |
| `product_embedding` | 商品 ID、名称、品类、价格、`embedding`、源数据版本号 | 语义导购；版本号用于同步对账 |
| `chat_memory` | 会话 ID、角色、内容、时间 | 会话记忆（用 Spring AI 的 JDBC 会话记忆实现） |
| `ai_tool_call_log` | 会话、用户、工具、参数、结果摘要、耗时、token、是否被拦截 | 审计、成本统计、评测数据源 |
| `semantic_cache` | 问题 `embedding`、标准答案、命中次数、失效时间 | 高频问题缓存 |
| `eval_run` / `eval_case_result` | 运行 ID、提交号、模型、用例结果 | 评测 |

## 功能模块

### 模块 1：售后对话助手（买家侧，核心）

- **查询**：我的订单、物流、退货进度（只读工具）
- **政策问答**：七天无理由的条件、运费谁出、多久到账（混合检索 RAG，回答附条款编号）
- **发起退货**：多轮收集信息（哪个订单、哪件商品、原因、图片）→ 生成草稿 → **用户点确认后**才提交
- **转人工**：识别到用户情绪激动、连续两轮没解决、或超出能力范围时，生成对话摘要转人工

### 模块 2：客服预审（客服侧）

新退货申请进来后，Agent 读取订单、商品、物流、政策，给出"建议同意/拒绝 + 理由 + 引用条款"。客服在后台一键采纳或修改，**状态变更由客服点击触发**。

### 模块 3：意图路由与模型路由

用户每条消息先经过小模型做意图分类（结构化输出）：`查询订单 / 政策问答 / 申请退货 / 商品导购 / 闲聊 / 转人工`。不同意图挂不同的工具集和提示词，只有退货判断、预审这类复杂推理才调用大模型。

面试价值：能给出"路由前后单次会话平均成本下降多少、意图分类准确率多少"这样的数字。

### 模块 4：语义导购（加分模块，落后时第一个砍）

"想要一双适合跑步、500 元以内的鞋"→ 小模型用结构化输出抽出筛选条件 `{品类: 跑鞋, 价格上限: 500}` → PostgreSQL 里 SQL 过滤 + 向量相似度排序 → 返回商品卡片。

这需要把商品数据从 MySQL 同步到 PostgreSQL，正好引出一个经典后端问题（见下文"跨库同步"）。

### 不做

- 不做多 Agent（单 Agent + 意图路由足够，面试时能讲清为什么不拆）
- 不微调模型
- 不做复杂前端（聊天页和客服预审页用原生 HTML/JS）

## 核心设计一：工具层的五道防线

面试大部分追问会落在这里。下面这张时序图把前三道防线串成一条完整链路，**面试时被要求"画一下"就画这张**：

![退货两阶段提交时序](../diagrams/return-flow/preview.png)

可交互版本：[return-flow.html](../diagrams/return-flow/return-flow.html)。

### 1. 身份注入，防越权

**问题**：工具 `getOrder(orderId)` 的参数由 LLM 生成。用户说"帮我查订单 10086"，而 10086 是别人的；或者 prompt 里藏了注入指令让模型去查别人的订单。

**做法**：工具签名里**没有 userId 参数**。userId 从当前登录态（JWT）在服务端注入，查询时强制 `WHERE member_id = 当前用户`。LLM 无论生成什么参数都碰不到别人的数据。

**验证**：用户 A 的会话里要求查用户 B 的订单号，断言返回"未找到"。

### 2. 读写分级 + 用户确认

只读工具自动执行；写工具只生成**待确认草稿**并推给前端，用户点确认后由普通接口执行，**确认这一步不经过 LLM**。客服侧同理。

### 3. 幂等

LLM 超时重试、用户狂点确认、网络重放，都可能重复提交。每个写操作带幂等键（草稿 ID），Redis `SET key NX EX` 挡并发，MySQL 唯一索引兜底；退款消息的消费端按业务 ID 去重。

**验证**：同一个确认请求并发 10 次，只生成 1 条申请。

### 4. 审计

每次工具调用写 `ai_tool_call_log`。出了问题能追溯"Agent 当时看到了什么、为什么这么做"，同时是成本统计和评测的数据源。

### 5. 限流与成本

Redis 令牌桶按用户限制每分钟请求数，外加每日 token 预算。超出后降级为转人工。

## 核心设计二：混合检索 RAG

1. **入库**：售后政策 Markdown/PDF → 按条款切块（保留条款编号和标题层级）→ embedding → 写入 `kb_chunk`，同时生成中文全文索引（zhparser 分词；镜像需要自己构建，起步可先用 `pg_trgm`）
2. **检索**：同一个问题走两路，向量检索 top 20 + 全文检索 top 20，用 RRF 融合取 top 5
3. **生成**：提示词要求只依据检索到的条款回答，并输出引用的条款编号；检索不到就明确说不知道并转人工
4. **评估**：准备 30 个问题 + 标准条款，统计 Recall@5；对比纯向量、纯关键词、混合三种方式

Embedding 模型选一个中文效果好的（如 bge-m3、通义 text-embedding 系列），**维度定下来就不要换**，换了要全量重建索引。

## 核心设计三：语义缓存

高频问题（"多久到账""运费谁出"）占了大部分流量。问题向量和 `semantic_cache` 里的历史问题做相似度比较，超过阈值直接返回缓存答案。

要处理的细节：

- **阈值**：太低会答非所问，太高命中率低，用评测集调
- **个性化问题不缓存**：带订单号、涉及个人信息的问题直接跳过
- **失效**：政策文档更新时清掉相关缓存

## 核心设计四：护栏

| 位置 | 做什么 |
|---|---|
| 输入 | 检测 prompt 注入特征（"忽略之前的指令"等）；手机号、地址、身份证号**脱敏后再发给外部模型** |
| 工具 | 五道防线 |
| 输出 | 结构化输出做 Schema 校验；业务规则校验（不能承诺政策外的退款金额、不能编造条款编号） |

## 核心设计五：跨库同步（MySQL → PostgreSQL）

**问题**：商品在 mall 后台被修改后，PostgreSQL 里的商品向量也要更新。如果"写 MySQL 成功、发消息失败"，两边就不一致了。

**做法**：

1. 商品修改的事务里同时写一条本地消息表记录（Outbox），事务提交后由定时任务把消息投递到 RabbitMQ，投递成功再标记
2. AI 模块消费消息，重新生成 embedding，按版本号 upsert 进 `product_embedding`（版本号保证旧消息不会覆盖新数据）
3. 每天跑一次对账任务，比较两边的版本号，补齐漏掉的

面试时能讲出"为什么不直接在业务代码里发 MQ""为什么还要对账""CDC（Canal / Debezium）方案和你的方案怎么比"。

## 其他技术点

| 技术点 | 做法 |
|---|---|
| 流式输出 | `SseEmitter`；Nginx 对 `/ai/` 关闭 `proxy_buffering` |
| 会话记忆 | 最近 N 轮放 Redis 加速，全量持久化到 PostgreSQL；超长会话做摘要压缩 |
| 退款异步 | 客服同意后发 RabbitMQ；生产者确认 + 手动 ack + 消费幂等 |
| 订单超时取消 | mall 已有，读懂即可 |
| 可观测 | Spring AI 的 Micrometer 埋点 → OpenTelemetry → Langfuse；看板按意图拆分延迟、token、成本 |
| 压测 | JMeter 压普通查询接口（加缓存前后对比）；AI 接口记录首字延迟（TTFT）和单次成本 |

## 面试会被追问的问题（准备答案）

1. 为什么不让用户直接在页面上点"申请退货"，非要加个 Agent？
2. 为什么是单 Agent + 意图路由，而不是多 Agent？
3. LLM 生成了错误的订单号会怎样？prompt 注入让它查别人的订单呢？
4. 幂等键是谁生成的？Redis 挂了怎么办？
5. 为什么用两个数据库？跨库数据不一致怎么办？为什么不用 Canal？
6. pgvector 的 HNSW 索引参数怎么选？数据量到千万级还能用吗？
7. 为什么要混合检索？RRF 的原理是什么？
8. 语义缓存的阈值怎么定？误命中了怎么办？
9. 意图分类错了会怎样？怎么兜底？
10. 一次对话的延迟和成本是多少？瓶颈在哪？
11. 评测集怎么构造的？LLM 判分可信吗？
12. 并发 100 个用户同时用售后助手，哪里先扛不住？
